# Инструкции ИИ-агенту: Kodik API

Эти правила обязательны при разработке, изменении и тестировании интеграции Kodik в проекте.

## 1. Обязательный порядок чтения

- Начни с [`README.md`](README.md).
- Прочитай документацию конкретного endpoint до написания клиента или DTO.
- Для общих параметров используй [`parameters/parameter-index.md`](parameters/parameter-index.md) и [`parameters/common.md`](parameters/common.md).
- Проверяй исходный код проекта перед выбором архитектуры, имен классов, HTTP-клиента, конфигурации, логирования и тестового фреймворка. Не вводи новые соглашения, если проект уже определил существующие.

## 2. URL и секреты

- Базовый URL: `https://kodik-api.com`.
- Формируй URL как базовый URL + путь endpoint из документации.
- Передавай `token` способом, предусмотренным документацией конкретного endpoint и существующей реализацией проекта. Не предполагай способ передачи токена, если он не подтверждён.
- Не хардкодь токен и не коммить секреты. Используй конфигурацию и переменные окружения по соглашениям проекта.
- Не выводи токен в логах, исключениях, трассировках и тестовых снапшотах.

## 3. Контракт API

- Считай документацию endpoint основным источником его параметров и полей ответа.
- Не смешивай параметры запроса `/list` и `/search`: даже если имена совпадают, смысл, обязательность и ограничения могут различаться.
- Не отправляй неизвестные параметры «на всякий случай».
- Соблюдай документированные типы, допустимые значения, значения по умолчанию и ограничения.
- Параметры со списками передавай в формате, описанном для конкретного параметра (например, через запятую только там, где это указано).
- Не считай, что несколько ID всегда означают логическое AND: для `/search` описание отдельно указывает поведение поиска по нескольким внешним ID.
- Не считай ответ коллекцией без проверки фактической структуры ответа и схемы, указанной в документации.
- Если в документации не описаны HTTP-коды, ошибки, rate limits, таймауты или правила повторов, не выдумывай их. Реализуй осторожное поведение на основе соглашений проекта и зафиксируй предположение.

## 4. Поиск и выгрузка материалов

- Используй `/search` для поиска материалов по названию, Kodik ID, ссылке на плеер или внешним идентификаторам — согласно [`methods/search.md`](methods/search.md).
- Используй `/list` для выборки по фильтрам и постраничного обхода — согласно [`methods/list.md`](methods/list.md).
- Не подменяй `/search` методом `/list` только потому, что у них есть похожие фильтры.
- При массовой выгрузке учитывай `limit` и механизм продолжения/пагинации, описанные для `/list`. Не предполагай, что один запрос возвращает весь каталог.
- Запрашивай поля сезонов и серий только если они нужны: смотри `with_seasons`, `with_episodes` и `with_episodes_data` в документации `/list`.
- Не полагайся на порядок выдачи, если он не задан параметрами запроса или документацией.

## 5. DTO и преобразование данных

- Разделяй DTO ответа API и доменные модели проекта, если это соответствует текущей архитектуре.
- Сохраняй исходные внешние идентификаторы и провайдера (`kodik`) в соответствии с существующей моделью источников проекта; не используй внешние ID как внутренние primary key без явного решения проекта.
- Обрабатывай отсутствующие и nullable поля в соответствии с документацией и реальными ответами. Не превращай отсутствующее значение в фиктивное значение без доменного основания.
- Не делай предположений о том, что название уникально. Для связывания сущностей предпочитай документированные стабильные идентификаторы, когда они доступны.
- Не выполняй неявное преобразование типов, если оно может потерять информацию (например, строковые ID в числа).

## 6. Надёжность и безопасность

- Используй HTTP-клиент и настройки проекта.
- Учитывай таймауты, ошибки транспорта, неуспешные HTTP-ответы и некорректный JSON. Не маскируй ошибку как пустой успешный результат.
- Повторы допустимы только для безопасных запросов и с ограничением числа попыток; не добавляй бесконечные циклы.
- Не логируй секреты и чувствительные параметры.
- Для импорта делай обработку повторного запуска идемпотентной, если это согласуется с бизнес-логикой проекта.
- Не добавляй миграции, модели, сервисы или новые зависимости до проверки существующих аналогов в проекте.

## 7. Тестирование

- Добавляй тесты для успешного ответа, пустой выдачи, необязательных/отсутствующих полей и ошибок HTTP/JSON.
- Используй HTTP fake/mock и фабрики проекта вместо реальных вызовов Kodik в автоматических тестах.
- Не требуй настоящего API-токена для unit-тестов.
- Проверяй сериализацию query-параметров, особенно массивов, boolean-значений, ID и параметров пагинации.
- Тесты должны подтверждать контракт, а не случайные детали реализации.

## 8. Неопределённости

Если задача требует сведений, которых нет в этих файлах:
1. Найди ближайший endpoint/параметр в документации.
2. Проверь актуальный код проекта и существующие тесты.
3. Если неопределённость остаётся, явно обозначь её и попроси уточнение либо изолируй предположение в одном месте кода.
4. Не выдумывай API-поля и не меняй контракт ради удобства реализации.

## 9. Завершение задачи

В итоговом отчёте кратко укажи:
- какие файлы изменены;
- какие решения/предположения сделаны;
- какие тесты запущены и их результат;
- какие вопросы по контракту API остались открыты.
