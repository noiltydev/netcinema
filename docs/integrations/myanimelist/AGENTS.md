# Инструкции ИИ-агенту: MyAnimeList API

Эти правила обязательны при разработке, изменении и тестировании интеграции MyAnimeList в проекте.

## 1. Обязательный порядок чтения

- Начни с [`README.md`](README.md).
- Прочитай документацию конкретного endpoint до написания клиента или DTO.
- Для общих параметров используй [`parameters/parameter-index.md`](parameters/parameter-index.md) и [`parameters/common.md`](parameters/common.md).
- Проверяй исходный код проекта перед выбором архитектуры, имен классов, HTTP-клиента, конфигурации, логирования и тестового фреймворка. Не вводи новые соглашения, если проект уже определил существующие.

## 2. URL и секреты

- Базовый URL: `https://api.myanimelist.net/v2`.
- Формируй URL как базовый URL + путь endpoint из документации.
- Аутентификация: OAuth2 (implicit flow, scope `write:users`) — передавай `Authorization: Bearer <ACCESS_TOKEN>`; либо Client ID — заголовок `X-MAL-CLIENT-ID: <CLIENT_ID>`.
- Не хардкодь токены и Client ID, не коммить секреты. Используй конфигурацию и переменные окружения по соглашениям проекта.
- Не выводи токены в логах, исключениях, трассировках и тестовых снапшотах.

## 3. Контракт API

- Считай документацию endpoint основным источником его параметров и полей ответа.
- Не смешивай параметры запроса разных endpoint: даже если имена совпадают, смысл, обязательность и ограничения могут различаться (например, `status` в `/users/@me/animelist` и `/users/@me/mangalist` имеют разные допустимые значения).
- Не отправляй неизвестные параметры «на всякий случай».
- Соблюдай документированные типы, допустимые значения, значения по умолчанию и ограничения.
- Параметр `fields`: запрашивай только нужные поля; вложенные поля указывай в фигурных скобках (например, `my_list_status{status,score,num_episodes_watched}`).
- Параметр `nsfw`: по умолчанию NSFW-контент не возвращается; явно устанавливай `nsfw=true` при необходимости.
- Не считай ответ коллекцией без проверки фактической структуры ответа и схемы, указанной в документации (ответ обёрнут в `{data: [...], paging: {...}}`).
- Если в документации не описаны HTTP-коды, ошибки, rate limits, таймауты или правила повторов, не выдумывай их. Реализуй осторожное поведение на основе соглашений проекта и зафиксируй предположение.

## 4. Работа со списками (animelist / mangalist)

- Используй `GET /anime` или `GET /manga` для поиска и фильтрации каталога — согласно соответствующим файлам в `methods/`.
- Используй `GET /users/{user_name}/animelist` или `GET /users/{user_name}/mangalist` для получения списка пользователя — с фильтрами `status`, `sort`, `limit` (до 1000), `offset`.
- Для собственного списка используй `user_name=@me` (требует OAuth2).
- При массовой выгрузке учитывай `limit` и механизм пагинации через `paging.next` / `paging.previous`. Не предполагай, что один запрос возвращает весь каталог.
- Не полагайся на порядок выдачи, если он не задан параметрами запроса или документацией.

## 5. DTO и преобразование данных

- Разделяй DTO ответа API и доменные модели проекта, если это соответствует текущей архитектуре.
- Сохраняй исходные внешние идентификаторы и провайдера (`mal`) в соответствии с существующей моделью источников проекта; не используй внешние ID как внутренние primary key без явного решения проекта.
- Обрабатывай отсутствующие и nullable поля в соответствии с документацией и реальными ответами. Не превращай отсутствующее значение в фиктивное значение без доменного основания.
- Не делай предположений о том, что название уникально. Для связывания сущностей предпочитай документированные стабильные идентификаторы (MAL ID), когда они доступны.
- Не выполняй неявное преобразование типов, если оно может потерять информацию (например, строковые ID в числа).
- Поля `*_formatted` (например, `relation_type_formatted`) предназначены для отображения пользователю и могут меняться — не используй их для логики.

## 6. Надёжность и безопасность

- Используй HTTP-клиент и настройки проекта.
- Учитывай таймауты, ошибки транспорта, неуспешные HTTP-ответы и некорректный JSON. Не маскируй ошибку как пустой успешный результат.
- Повторы допустимы только для безопасных запросов (GET) и с ограничением числа попыток; не добавляй бесконечные циклы.
- Не логируй секреты и чувствительные параметры.
- Для импорта делай обработку повторного запуска идемпотентной, если это согласуется с бизнес-логикой проекта.
- Не добавляй миграции, модели, сервисы или новые зависимости до проверки существующих аналогов в проекте.

## 7. Тестирование

- Добавляй тесты для успешного ответа, пустой выдачи, необязательных/отсутствующих полей и ошибок HTTP/JSON.
- Используй HTTP fake/mock и фабрики проекта вместо реальных вызовов MAL в автоматических тестах.
- Не требуй настоящего API-токена для unit-тестов.
- Проверяй сериализацию query-параметров, особенно массивов, boolean-значений, ID, параметров пагинации и `fields`.
- Тесты должны подтверждать контракт, а не случайные детали реализации.

## 8. Неопределённости

Если задача требует сведений, которых нет в этих файлах:
1. Найди ближайший endpoint/параметр в документации.
2. Проверь актуальный код проекта и существующие тесты.
3. Если неопределённость остаётся, явно обозначь её и попроси уточнение либо изолируй предположение в одном месте кода.
4. Не выдумывай API-поля и не меняй контракт ради удобства реализации.
